## 一、整体架构：把“业务算法”和“执行管理”彻底分开

建议分成三层：

| 层次        | 负责什么                               | 不应该负责什么                |
| --------- | ---------------------------------- | ---------------------- |
| **控制层**   | 调度、版本分配、输入选择、血缘、日志、重试、状态、发布        | 不直接实现 OCR、修复和语音模型      |
| **节点策略层** | 用某一种方法完成一个节点，产出标准结果                | 不自行决定跳过、不覆盖旧版本、不选择下游输入 |
| **执行工具层** | 调用 yt-dlp、FFmpeg、模型 API 或独立 worker | 不拥有整条视频的业务状态           |

项目结构如下，包中已有对应的核心代码：

```text
bivideo/
├── src/bivideo/
│   ├── cli.py              # 导入、下载、节点执行、重试、查询历史
│   ├── acquire.py          # yt-dlp 下载与获取记录
│   ├── store.py            # SHA-512 目录、版本、产物引用、SQLite 索引
│   ├── contracts.py        # 插件接口、产物契约、基础校验
│   ├── engine.py           # 节点执行、血缘、发布、强制重试
│   ├── worker.py           # 独立进程调用、超时、请求响应协议
│   ├── plugins.py          # 已实现节点及契约测试插件
│   ├── timeline.py         # 空档优先时间线，确定性纯函数
│   ├── media.py            # FFmpeg 参考合成与结构验证
│   └── util.py             # 哈希、原子写入、代码身份、路径限制
├── schemas/                # 标准数据格式
├── configs/                # DAG 蓝图、策略和真实测试配置
├── scripts/                # worker 示例、上游版本锁定
├── tests/
├── docs/
└── verification/           # 本次实际测试证据
```

生产版本再增加 `orchestration/`、`adapters/`、`nodes/`、`quality/` 等模块，**但不改变已经确定的产物、执行版本和血缘协议**。

主程序不需要同时安装所有 AI 依赖。OCR、视频修复、语音模型分别使用独立环境或 worker，主程序通过标准请求和结果文件与其通信。

## 二、业务流程：下载之后，每个环节做什么？

完整设计拆成了 24 个节点。下面按业务阶段合并展示：

| 阶段              | 节点及职责                                 | 主要产物                |
| --------------- | ------------------------------------- | ------------------- |
| **1. 获取与归档**    | yt-dlp 下载媒体和已有字幕；校验文件；计算源文件 SHA-512   | 原视频、获取记录、旁挂字幕、下载元数据 |
| **2. 媒体分析与归一化** | 检查音视频流、语言、帧率、PTS、旋转、色彩；建立工作视频、音频和时钟映射 | 媒体信息、工作视频、工作音轨、帧索引  |
| **3. 字幕证据提取**   | 提取软字幕；检测硬字幕区域；OCR；合并重复显示事件            | 原文、时间、字框、置信度、原始截图   |
| **4. 语音分析与分句**  | 检测全部原始讲话；ASR、词级对齐、说话者和重叠；关联字幕并形成朗读单元  | 语音地图、完整语句、安全边界      |
| **5. 字幕清理**     | 根据目标区域构造掩膜；修复背景；检查残字、误擦和明显闪烁          | 掩膜、无字幕视频、清理质量报告     |
| **6. 样式恢复**     | 原字体候选、颜色、字重、描边和阴影；选择中文字体及检查字形覆盖       | 样式表、字体证据和匹配状态       |
| **7. 模型处理**     | LLM 翻译；选择同说话者参考；语音模型生成各语言音频           | 译文、参考音频、模型请求响应、原始译音 |
| **8. 译音标准化与检查** | 解码、重采样、检查首尾静音、测量实际长度；回识别检查漏读、重复等      | 标准译音、实际采样数、单段质量报告   |
| **9. 时间线规划**    | 优先利用原片空档，只有不足时才补帧                     | 原片到成片的映射、定格区间、译音区间  |
| **10. 双语排版与合成** | 英文在上、中文在下；映射新时间；按计划合成画面和声音            | ASS、成片、合成清单         |
| **11. 最终检查与发布** | 完整解码、顺序、音画长度、字幕、声音和视觉检查               | 成片版本、QA、血缘清单、发布状态   |

### 两条流程约束很重要

**先提取字幕证据，再去字幕。**
否则原字体、字框和截图证据已经被擦掉，后续只能重新猜。

**字幕时间与讲话时间分别管理。**
字幕消失不代表讲话结束；没有字幕也不代表没有人讲话。语音分析需要保护全部原始讲话，而不是只保护成功提取到字幕的部分。WhisperX 可作为词级对齐的参考，但重叠讲话等情况仍需要项目自己的边界判断。([GitHub][1])

## 三、SHA-512 目录：聚合的是“源文件字节”，不是 YouTube URL

建议明确采用：

```text
asset_sha512 =
SHA512(
    下载完成并合并音视频之后，
    任何归一化、字幕清理或重新编码之前，
    原始媒体文件的全部字节
)
```

因此：

**相同文件内容，即使文件名不同，进入同一个目录。**

**相同 YouTube 页面，如果下载格式、音轨或封装字节不同，可能进入不同目录。**不能把 URL 相同当成 SHA-512 相同；归一化后的文件也不能反过来取代源身份。

### 下载前未知 SHA，必须有临时获取区

这一点不能省略：下载尚未完成时，程序不知道最终文件的 SHA-512。

建议目录：

```text
data/
├── acquisitions/
│   └── <acquisition_id>/       # 尚未确定源 SHA 的下载
│       ├── request.json
│       ├── runtime.json
│       ├── stdout.txt
│       ├── stderr.txt
│       └── 临时下载文件
│
└── videos/
    └── <source_sha512>/
        ├── source/
        │   └── original.bin
        ├── acquisitions/      # 成功确认源身份后归档的获取证据
        ├── nodes/
        ├── selections/
        ├── pipeline.jsonl
        └── index.sqlite
```

下载成功后，将获取记录、旁挂字幕等归档到对应源目录。

**下载失败且还没有完整媒体时，不能强行归入一个猜测的 SHA 目录。**失败记录保留在获取区；后续成功确认身份后，可以按明确的重试关系归并历史证据。

模型权重、工具安装目录、共享字体库不属于某个视频独占的处理产物，可以放在公共只读依赖区；每次使用时记录其版本及摘要。

## 四、节点版本：不要把“执行身份”和“内容指纹”混成一个东西

建议至少区分以下身份：

| 身份                            | 用途              |
| ----------------------------- | --------------- |
| `asset_sha512`                | 哪个原始视频          |
| `node + item`                 | 哪个业务节点、哪个处理单元   |
| `attempt_id + version`        | 这一次实际执行         |
| `strategy_id + code identity` | 用哪一种实现、哪一版代码    |
| `ArtifactRef`                 | 精确引用哪次执行产生的哪个文件 |

其中 `item` 用于处理粒度。例如：

```text
OCR：item=all，或明确的分块ID

语音生成：item=<朗读单元ID>.<目标语言>

整片合成：item=all
```

同一个节点的每次执行：

```text
nodes/
└── caption_extract/
    └── all/
        ├── v000001_<attempt_A>/
        ├── v000002_<attempt_B>/
        └── v000003_<attempt_C>/
```

每个执行目录保存：

```text
request.json       # 固定输入引用、策略、代码、有效参数
runtime.json       # Python、设备、依赖和运行环境
work/              # 原始响应、截图、临时结果、stdout/stderr
artifacts/         # 校验通过后发布给下游的文件
result.json        # 状态、耗时、文件清单、哈希、错误
```

**即使三次输出的文件内容完全一样，也保留三次执行版本。**文件内容摘要相同，只能说明结果相同，不能说明后两次可以省略。

### 文件血缘必须是精确引用

下游不能只保存：

```text
输入：ocr/latest/captions.json
```

而应保存类似：

```json
{
  "asset_sha512": "<源视频SHA-512>",
  "producer_attempt_id": "<具体执行ID>",
  "name": "captions",
  "schema": "CaptionSet.v1",
  "path": "nodes/caption_extract/all/v000002_.../artifacts/captions.json",
  "sha512": "<这个字幕文件的SHA-512>",
  "bytes": 12345
}
```

这样才能回答：

> 这条中文字幕来自哪份 OCR？那份 OCR 用的哪个模型、哪组参数、哪个原始视频版本？

## 五、策略、模型与参数：记录实际执行身份，而不是一个模糊名称

你要求的“Git commit＋策略标识＋参数＋日志”，设计中保留，并进一步细化：

| 类别        | 应保存的信息                               |
| --------- | ------------------------------------ |
| 主项目代码     | Git commit、dirty 状态、代码树摘要            |
| 节点策略      | 节点名、策略 ID、策略版本、接口版本                  |
| 外部 worker | 上游 commit、本地 patch commit/摘要、构建或镜像身份 |
| 参数        | **默认值展开后的有效参数**，不是只有用户覆盖的几个值         |
| 模型        | 提供者、请求模型名、实际观察到的版本、权重摘要或 revision    |
| 推理过程      | 提示词、参考音频引用、种子、生成参数、请求和响应、服务端请求 ID    |
| 环境        | 依赖版本、设备、精度、运行后端、相关工具版本               |
| 输出        | 文件清单、每个文件摘要、耗时、状态、质量问题               |

例如 `paddle_ocr` 不只记录模型名称，还要记录检测阈值、识别阈值、缩放、抽帧、字幕合并策略等。

**远端模型没有提供实际权重版本时，要明确写未知。**不能把一个可变模型别名当成固定权重版本。

包中的参考骨架已经带有自身的真实 Git 提交及代码树摘要，并附 `SOURCE.bundle`；这不等于已经锁定所有外部项目。上游代码候选表中无法确认的 commit 保持为空，另提供锁定脚本，避免用假版本填满血缘字段。

## 六、插件替换：让下游依赖结果格式，而不是 OCR 实现

以 OCR 为例：

```text
paddle_ocr ─────┐
               ├─ CaptionSet.v1 ─→ utterance_build
qwen_vl_ocr ────┤
               │
videocr ────────┘
```

生产版 `CaptionSet.v1` 至少包含：

```text
输出契约版本
坐标所依据的画布尺寸
时间所依据的 clock_id

每条字幕：
  本地产物内唯一ID
  原始文字
  显示起止时间
  字框/区域
  置信度及其来源
  原图/原始OCR响应引用
  提取方式
```

**缺失信息允许明确缺失，但不允许伪造。**例如某个 VLM 没提供可靠字框或置信度，不能自动填全屏框和 `1.0`。需要这些信息的后续节点应补充检测或返回 `REVIEW`。

PaddleOCR 当前提供 `predict/predict_iter` 图片推理接口，VideOCR 则已经包含视频输入、字幕裁剪、抽帧及合并相关参数；可以分别包装为不同策略，统一转换结果。

### 插件不拥有执行控制权

插件只负责：

```text
读取已指定的输入
→ 执行业务
→ 在本次工作目录产出文件
→ 返回标准结果
```

以下行为由控制层禁止：

```text
发现输入没变，返回旧结果
发现输出文件存在，直接成功
覆盖其他执行目录
自行读取 latest
修改上游文件
替下游选择输入版本
```

独立 worker 接收唯一的请求文件，返回相同的 `attempt_id` 和结果清单。主程序负责超时、退出码、schema、路径及摘要检查。**这个进程接口是依赖隔离，不自动构成安全沙箱。**

## 七、重试：无条件重新执行，但不与“恢复”“选择旧版本”混淆

核心规则已经在参考代码中实现并测试：

> **每次有效的 `retry` 都产生新的 attempt，调用一次节点业务。没有输入指纹缓存分支。**

这里需要区分四个动作：

| 动作            | 是否重新运行业务            | 应产生什么             |
| ------------- | ------------------- | ----------------- |
| `run / retry` | **是**               | 新执行版本、新请求、新结果、新日志 |
| `select`      | 否                   | 新的版本选择清单          |
| 恢复整条工作流       | 尚未完成的节点执行；已固定产物明确引用 | 新流程记录             |
| 恢复文件发布事务      | 否                   | 完成已写盘产物的元数据发布     |

例如 OCR 已经执行 A、B 两种策略：

```text
A → captions_A
B → captions_B
```

选择 `captions_B` 不叫“重试 OCR”；它只是明确选用 B 的结果。

同样，某个中文音频重试生成了新版本，**旧成片不会自动变化**。只有选中新音频，才重新执行依赖它的时间线、字幕布局、合成和最终 QA。

允许保留模型已加载的权重、连接池等资源；**不允许复用旧推理结果冒充新执行**。对于远端 API，能够保证的是发出新的业务请求并保留调用证据，不能保证提供者内部不可观察的计算过程一定完全重做。

## 八、日志和崩溃恢复：不能只在成功时写一句“完成”

每个视频的主日志为：

```text
videos/<SHA-512>/pipeline.jsonl
```

每个节点至少记录：

```text
NODE_STARTED
INPUTS_VALIDATED
PLUGIN_INVOKED / WORKER_STARTED
关键处理事件或模型调用ID
OUTPUTS_VALIDATED
NODE_SUCCEEDED / NODE_FAILED
```

事件包含节点、单元、attempt、版本、输入引用、代码身份、策略、有效参数、输出引用、时间和耗时。

大体积 OCR 原始结果、模型响应及 stderr 放入该次执行目录，主日志保存其引用，不把所有内容重复塞进一行 JSON。

### 发布结果需要两阶段考虑

推荐顺序是：

```text
完成业务
→ 校验输出
→ 持久化文件与清单
→ 数据库登记成功产物
→ 下游可见
```

**文件系统和 SQLite 不是同一个事务。**如果文件写完但数据库登记前进程崩溃，应恢复发布，而不是把原业务算作失败后悄悄再调用一次模型。

详细设计给出了相关状态、恢复窗口和故障测试。当前骨架已有日志投影重建，但**生产级孤儿任务识别、租约和完整发布恢复器仍需补齐**。

## 九、时间线：完全按你确认的“空档优先”策略

对于第 \(i\) 段英文：

```text
英文结束：E
下一段英文开始：S
中文实际音频长度：C
原片可用空档：G = S − E
```

额外延长：

$$
H=\max(0,\;1+C+1-G)
$$

实际实现再按输出帧率补齐，音频使用采样数管理，不反复累加浮点秒。

### 例子

```text
英文A：2～5秒
英文B：8～9秒
中文A：4秒
```

只有 3 秒空档，需要 6 秒，所以补 3 秒：

```text
5～6秒：等待，画面正常走
6～8秒：中文前半段，画面正常走
8～10秒：中文后半段，保持下一句英文前的画面
10～11秒：继续保持，等待1秒
11秒：英文B和它对应的原画面一起恢复
```

需要特别保证：

**中文音频跨越“正常播放→定格”的边界时，仍是连续的一段音频。**

**下一句原声和原画面顺延相同的时长。**

**空档足够就不加定格，更不剪掉多余原片。**

**最后一段先利用片尾，不够再延长最后一帧。**

FFmpeg 可以承担切片、时间戳调整、补帧和拼接；例如 `tpad` 支持延长最后一帧。但缺口计算、音画映射和字幕安排属于新项目的时间线逻辑。([FFmpeg][2])

参考实现还处理了有理数帧率下的累计取整，避免把每段的采样舍入误差累加成长期漂移。

# 一、整体架构：稳定内核与可替换业务节点分离

建议把项目分成三个层次：

```text
业务配方层
决定执行哪些节点、使用哪个策略、消费哪个产物版本
                         ↓
稳定执行内核
资产 / 执行版本 / 血缘 / 日志 / 重试 / 插件协议 / 发布
                         ↓
业务策略层
yt-dlp / OCR / ASR / 去字幕 / 字体 / LLM / 克隆语音 / FFmpeg
```

**核心原则是：插件可以改变处理方法，但不能改变执行、版本和持久化规则。**

例如，OCR 插件只负责读取指定输入并产出标准字幕数据。它不负责决定版本号，不允许覆盖旧结果，不允许自行读取历史结果后把“复用缓存”包装成一次新执行。

## 已搭建的项目骨架

```text
video_interleave_v2/
├── vidflow/
│   ├── cli.py          # 导入、下载、执行、重试、恢复、配方运行
│   ├── acquire.py      # yt-dlp 下载与下载后归档
│   ├── store.py        # SHA512目录、SQLite、版本、血缘、日志
│   ├── engine.py       # 节点执行器和插件注册
│   ├── pipeline.py     # 显式输入版本的 DAG 配方
│   ├── contracts.py    # JSON Schema及部分语义校验
│   ├── plugins.py      # 已实现策略和外部worker适配器
│   ├── timeline.py     # 空档优先时间线纯函数
│   ├── media.py        # FFmpeg参考合成器
│   ├── util.py         # 哈希、原子写、锁、源码指纹
│   └── demo.py         # 实际媒体验证样例
├── tests/
├── integration/
├── examples/
```

后续真实业务代码建议放到独立 worker 包中，例如：

首版采用**单机进程调度＋本地 SQLite＋文件目录**即可。SQLite WAL 不适合让多台机器通过网络文件系统共同访问，因此索引放本地磁盘，远程模型通过 worker 服务调用，而不是共同写 NAS 上的数据库。([SQLite][2])

# 二、业务流程：从 URL 到最终结果

完整设计把流程拆成独立节点，而不是一个巨大函数。

| 阶段   | 节点            | 做什么                            |
| ---- | ------------- | ------------------------------ |
| 获取   | **下载**        | yt-dlp 获取视频、字幕及元数据，保留下载日志      |
| 登记   | **源文件登记**     | 复制源快照、计算 SHA512、创建资产目录         |
| 媒体准备 | **探测与规范化**    | 检查音视频流、帧率、时间原点、旋转、色彩；建立统一工作时间域 |
| 字幕事实 | **字幕来源与区域识别** | 区分软字幕、硬字幕、混合字幕；确定目标字幕区域        |
| 字幕事实 | **OCR 提取**    | 保存原文字、出现时间、位置、截图、置信度           |
| 语音事实 | **语音识别与对齐**   | 获取实际讲话区间、词时间、说话者、重叠讲话区间        |
| 内容组织 | **归句与安全切点**   | 将多个字幕片段归为完整语句，确定不会截断语音的插入位置    |
| 画面处理 | **样式分析**      | 字体候选、字号、颜色、描边、阴影、位置及中文字体适配     |
| 画面处理 | **掩膜生成与去字幕**  | 只处理目标字幕区域，生成清理画面并检查残字          |
| 模型处理 | **翻译**        | LLM 按固定语句 ID 输出显示译文、朗读译文       |
| 模型处理 | **参考音频准备**    | 按说话者选择干净参考音频，保存准确转写与来源         |
| 模型处理 | **克隆语音生成**    | 外部语音模型生成目标语言音频                 |
| 音频准备 | **译音规范化与检查**  | 测量实际采样数、处理首尾静音、检查漏读或重复         |
| 编排   | **时间线规划**     | 利用原空档，只为不足部分补定格                |
| 编排   | **双语字幕排版**    | 英文在上、中文在下，映射到新时间线              |
| 合成   | **音频组织与视频渲染** | 原音保护、译音混合、定格、字幕烧录、编码           |
| 验收   | **最终质量检查**    | 结构、字幕、语音、内容和画面异常检查             |
| 发布   | **结果发布**      | 明确选择成片与 QA 版本，创建不可变发布记录        |

两个特别重要的设计点：

**第一，字幕显示时间和实际语音时间分别保存。** 不能用“字幕消失了”作为“原人声已结束”的唯一依据。WhisperX 可以参考其对齐能力，但其实现存在对齐失败后退回原分段时间的路径，因此“返回了时间戳”不等于“精确对齐已成功”。([GitHub][3])

**第二，画面和语音可以分支处理，但最后必须固定版本汇合。** 比如去字幕使用哪个掩膜版本、时间线使用哪组中文音频、字幕使用哪个译文版本，都必须是明确的 artifact 引用。

# 三、SHA512 持久化：一个源视频，一个资产目录

## 1. 下载前需要一个临时区域

**下载完成前，不可能提前知道完整视频的 SHA512。**

所以需要：

```text
YouTube URL
    ↓
incoming/<download_attempt_id>/
    ↓
下载、合流完成，确定实际最终文件
    ↓
计算整个文件的 SHA512
    ↓
videos/<完整128字符SHA512>/
```

yt-dlp 官方提供 `after_move` 阶段获取最终文件路径；应使用这一结果，而不是在合流前猜测最终扩展名。其当前 YouTube 支持还涉及 JS runtime/EJS 等依赖，需要在下载 worker 部署时一起验证和锁定。([GitHub][4])

下载失败且尚无完整文件时，记录保留在 `incoming`，不能伪造一个视频哈希目录。成功后再把此次下载历史归入对应资产。

**相同 URL 不保证相同 SHA512。** 不同分辨率、编码或合流文件字节不同，应产生不同资产；URL 和 YouTube video ID 作为来源信息保存，不替代文件身份。

## 2. 资产目录结构

```text
workspace/
├── incoming/
└── videos/<sha512>/
    ├── source/
    │   ├── original.bin
    │   └── source.json
    │
    ├── acquisitions/<获取ID>/
    │   ├── request.json
    │   ├── outcome.json
    │   ├── 下载元数据与字幕
    │   └── 原始下载日志
    │
    ├── index.sqlite
    ├── events.jsonl
    │
    ├── runs/<run_id>/
    │   ├── plan.json
    │   ├── steps/
    │   └── result.json
    │
    ├── nodes/<node>/<scope>/
    │   ├── v000001_exec_<id>/
    │   │   ├── request.json
    │   │   ├── source.snapshot.zip
    │   │   ├── artifacts/
    │   │   └── manifest.json
    │   ├── v000002_exec_<id>/
    │   └── ...
    │
    ├── selections/
    └── releases/
```

这里区分五种身份：

| 身份             | 作用              |
| -------------- | --------------- |
| `asset_id`     | 源视频完整 SHA512    |
| `run_id`       | 一次完整或局部流程运行     |
| `execution_id` | 某个节点某次实际执行      |
| `version`      | 同节点、同处理范围内的执行顺序 |
| `artifact_id`  | 某次执行产出的某一个文件    |

**artifact_id 不等于文件哈希。** 即使两次执行产生完全相同的文件，也有不同的产物身份和血缘。

# 四、每次执行保存什么，如何追溯到代码和模型？

每个节点执行前保存 `request.json`，执行结束保存 `manifest.json`。

至少保存：

```text
源视频 SHA512
run_id / execution_id / retry_of
节点名称 / 策略标识 / 节点版本
输入 artifact_id / 输入文件 SHA512
实际参数及其规范化 JSON 哈希
代码 git commit / dirty 状态 / 实际源码树哈希
实际源码快照
模型声明及实际调用回执
所有输出文件的路径 / 大小 / SHA512 / producer
开始时间 / 结束时间 / 耗时 / 状态
原始进程日志及模型请求响应
```

## 文件级血缘

例如某份字幕结果：

```json
{
  "id": "art_<本次唯一ID>",
  "name": "captions.json",
  "producer_execution_id": "exec_<本次执行>",
  "sha512": "<实际文件哈希>",
  "parents": [
    {
      "role": "video",
      "artifact_id": "art_<规范化视频版本>"
    },
    {
      "role": "roi",
      "artifact_id": "art_<字幕区域版本>"
    }
  ]
}
```

骨架采用保守的文件血缘：**每个输出文件关联该执行实际消费的全部输入**。后续可以增加帧区间、音频采样区间等精细来源，但不能凭空声称某个输出字一定来自某个像素。

## git commit 还不够

你的要求应扩展为：

```text
git commit
+ dirty 标记
+ 实际源码树哈希/快照
+ 策略标识
+ 参数
+ worker部署版本
+ 模型版本
+ 日志
```

原因是：**git commit 相同，不代表本地实际代码相同。** 未提交的改动也可能影响结果。

对于外部模型，还要区分：

```text
请求的模型名称
实际返回的模型名称/修订
模型权重哈希（本地模型可提供时）
参考音频版本
提示词及参数
供应商 request_id
```

供应商不公开具体权重版本时，记录“无法完全确定”，不能编造模型 revision。骨架已保存模型声明；真实服务的完整调用回执，需要由各模型适配器接入。

# 五、节点可替换：下游只认识标准结果

以 OCR 为例，下面两种策略：

```text
ocr / paddle_ocr
ocr / qwen_vl_ocr
```

都必须输出同一个 `captions.v1` 契约：

```json
{
  "schema": "captions.v1",
  "asset_sha512": "<源视频哈希>",
  "coordinate_space": "canonical_video_pixels",
  "cues": [
    {
      "cue_id": "c00018",
      "start_us": 12500000,
      "end_us": 14900000,
      "text": "This is an example.",
      "bbox_xyxy": [240, 860, 1670, 1010],
      "confidence": 0.96,
      "evidence": ["frames/c00018.png"]
    }
  ],
  "warnings": []
}
```

**下游不读取 Paddle 的内部对象，也不依赖某个视觉模型的响应格式。**

两种 OCR 比较时：

```text
相同规范化视频＋相同字幕区域
    ├── Paddle → OCR v1
    └── Qwen VL → OCR v2

独立比较结果
    ↓
显式选择某个 artifact
    ↓
下游绑定这个具体版本
```

不能在 v2 完成后，让正在运行的下游自动从 v1 切换到 v2。也不能用两份 OCR 的“第 18 行”认定它们是同一条字幕，必须按时间、内容等对齐。

VSE 和 VideOCR 的提取及合并流程可以参考，但适配层仍需导出这些统一字段；VSE 中的交互输入也需要移除或改为明确策略，不能直接放进无人值守流程。([GitHub][5])

# 六、无条件重试：执行与复用必须是两种不同操作

这里按照你的要求做了严格区分。

## `retry` 的含义

```text
创建新的 execution_id
→ 分配新的节点版本
→ 创建新的工作目录
→ 再次调用业务策略
→ 保存新的输入输出、日志和血缘
```

**没有这些判断：**

```python
if input_hash_unchanged:
    return old_result

if params_unchanged:
    skip()

if output_exists:
    reuse()
```

即使旧执行是成功状态，也允许重试。

当前骨架的重试会固定原输入版本和参数，使用当前安装的策略重新执行，同时记录当前代码版本。需要严格重放旧代码时，应明确部署旧 commit/镜像，而不能把当前代码重试当作旧版本重现。

## 显式使用历史产物不算“重试”

例如只想换字幕字体，不重新生成中文音频：

```text
新配方明确绑定旧 DubClip artifact
→ 执行新的排版
→ 执行新的合成
→ 执行新的 QA
```

这里没有安排 TTS 节点执行，因此不是“TTS 被缓存跳过”。

**一旦把 TTS 节点纳入本次执行，或者对它发出 retry，就必须再次调用模型。**

模型权重驻留、连接池可以复用；业务结果不能被缓存替代。外部供应商是否内部缓存通常不可完全控制，应记录其可观测行为，不能承诺供应商底层一定重新推理。

# 七、时间线：已按你的策略落成独立模块

时间线模块不需要 LLM 参与，它只消费：

```text
实际英文语音结束位置
下一段原始语音开始位置
安全视频帧切点
中文音频实际采样数
前后各1秒的配置
```

连续时间的基本公式仍然是：

$$
H_i=\max(0,\;1+C_i+1-G_i)
$$

实际执行还要考虑：**冻结必须发生在安全的视频帧边界，而不是任意音频时间点。**

因此真正计算使用安全切点 \(K_i\)：

$$
\text{补帧数}
=
\left\lceil
\max(0,\;\text{中文结束时间}+1-(K_i+\text{此前累计延长}))
\times fps
\right\rceil
$$

如果找不到不会截断原语音的安全帧边界，先重新归句或合并单元，不能强行插入。

FFmpeg 可以复用 `trim/atrim`、`setpts/asetpts`、`tpad` 和拼接能力；**决定补在哪里、补多少、如何保护原音**的逻辑由自己的时间线模块负责。([FFmpeg][6])

## 实际验证样例

本次用真实 FFmpeg 构造并处理了以下媒体样例：

| 语句 |   原语音区间 |      下一边界 | 中文长度 | 补足定格 |
| -- | ------: | --------: | ---: | ---: |
| u1 | 0.5～2 秒 |   下一句 6 秒 |  1 秒 |  0 秒 |
| u2 |   6～7 秒 |   下一句 9 秒 |  3 秒 |  3 秒 |
| u3 |  9～10 秒 | 原片结束 12 秒 |  2 秒 |  2 秒 |

结果为：

```text
原片：12秒 / 300帧
输出：17秒 / 425帧
额外定格：0 + 75 + 50帧
音频：48kHz / 816000个采样帧
```

不仅检查了长度，还检查了：

**每个原始画面按顺序保留；每个定格确实引用正确的前一帧；原音和译音的位置及内容与独立构造的期望结果逐采样一致。**

[查看实际验证报告](sandbox:/mnt/data/video_interleave_v2/evidence/TEST_RESULTS_ZH.md) · [查看合成样例](sandbox:/mnt/data/video_interleave_v2/evidence/demo/preview.mp4)

样例使用提示音，不是真实翻译语音；精确比对针对无损视频和 PCM，不是要求 H.264/AAC 编码字节与原片相同。

# 八、各开源项目具体参考什么，哪些自己开发？

完整源码定位和摘录已放在附件中。主要分工如下。

| 项目                           | 具体参考位置                                               | 复用内容                   | 自己开发的部分                          |
| ---------------------------- | ---------------------------------------------------- | ---------------------- | -------------------------------- |
| **yt-dlp**                   | `yt_dlp/YoutubeDL.py`、CLI/postprocessor 接口           | 视频/音频/字幕下载、格式选择、最终文件定位 | acquisition 版本、SHA512 归档、日志、重试政策 |

| **VideOCR**                  | `CLI/videocr_cli.py`                                 | CLI 参数化与字幕提取调用         | worker 协议、标准字框/截图输出、A/B 比较       |
| **VSR**                      | `backend/main.py`，`backend/tools/subtitle_detect.py` | 区域检测、连续掩膜区间、视频修复       | 独立 MaskTrack、禁止误擦、帧/时间校验         |
| **WhisperX**                 | `whisperx/alignment.py`、`diarize.py`                 | 对齐与说话者相关能力             | 原语音保护、安全帧切点、重叠归组                 |

| **pysubs2**                  | `ssafile.py`、`ssaevent.py`、样式对象                      | 字幕数据与读写                | 双语布局、换行、时间映射                     |
| **libass / fontTools**       | 渲染接口、`TTFont`                                        | ASS 渲染、字形覆盖检查          | 字体审计、实际边界检查、回退政策                 |
| **FFmpeg**                   | 滤镜及编码接口                                              | 切片、定格、混音、拼接、编码、基础检测    | gap-first 编排、同步规则、完整性验收          |
| **QCTools/qcli**             | CLI 分析报告                                             | 可选的基础质量分析              | 业务异常解释和最终质量门禁                    |

VSR 的修复能力值得作为独立 worker 复用，但不能继承其无区域时的全屏处理政策，也不应依赖它重新合入的音轨作为最终原音。([GitHub][7])

字体识别应定位为候选生成，而不是确定答案；YuzuMarker 的演示本身就是 top-k 候选。字幕渲染和字体读取则直接复用 libass、pysubs2 和 fontTools。([GitHub][8])

**不建议复用大型配音应用的缓存、任务状态、时间对齐和最终合成框架。** 这些正是你的特殊需求需要自己掌握的部分。

# 九、日志、恢复和自动验收

## 日志

每个资产有一份：

```text
videos/<sha512>/events.jsonl
```

保存节点开始、输入版本、策略/代码/参数、子进程调用、返回码、输出文件、耗时、终态等事件。

节点原始 stdout/stderr 和模型请求响应保存在各自版本目录中，通过汇总日志引用，不把所有大响应直接塞进一行日志。

## 恢复不等于重试

需要区分：

| 操作        | 行为                          |
| --------- | --------------------------- |
| `recover` | 修复已封存产物与数据库/日志之间的状态，不重新跑旧业务 |
| `retry`   | 新建执行版本，再次实际运行               |

文件系统和 SQLite 不是一个跨介质原子事务，所以设计了“先封存文件，再提交索引和事件，必要时恢复”的流程。不能简单写一句“原子保存”就忽略中断窗口。

骨架已经有基础恢复、日志半行修复和活跃执行锁保护；完整断电、磁盘满、远程 worker 迟到结果等故障矩阵仍列为生产验收任务。

## 自动检查不能只看程序成功退出

执行状态与质量状态分开：

```text
执行状态：SUCCEEDED / FAILED / ABANDONED
质量状态：PASS / REVIEW / FAIL / SKIPPED
```

例如 QA 程序成功运行并生成报告，但音色检查未执行：

```text
QA节点执行：SUCCEEDED
QA报告总体：REVIEW
```

**不能因为进程返回 0，就把未检查的成片发布为 PASS。**

QCTools 和 FFmpeg 可以提供基础检测，但“这段冻结是计划内的”“这段无声是要求的 1 秒间隔”等判断必须结合本项目时间线。([GitHub][9])

```bash
cd video_interleave_v2
```

需要本机 PATH 中存在 FFmpeg 和 ffprobe。

```bash
python -m pip install -e '.[download,test]'
```
